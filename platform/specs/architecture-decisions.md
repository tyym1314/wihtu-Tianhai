# 平台架构与界面决定 · 阶段 A

本文件记录已批准方案的实现基线。阶段 A 已完成界面、规格和独立灰盒预研；阶段 B 已实现本地 PostgreSQL、管理/会话API、参考钱包与两个概率游戏。实现矩阵见 phase-b-local-integration.md；下面的完整服务拆分仍是生产建设目标。

**应用边界。** 合作方、App 和环境共同决定所有读写范围。API 环境枚举固定为 `sandbox | production`；界面中 `live` 只是“生产设计预览”选项的内部值，正式调用必须映射到 `production`。用户唯一键为 `(partner_id, app_id, environment, external_user_id)`，币种与 wallet_scope 额外校验。目录共享，账户、余额、规则配置和对局不能隐式共享。

**服务结构。** React 管理端与开发者门户；模块化业务 API；独立多人房间进程；独立结算/对账任务进程。PostgreSQL 持久化正式业务，Redis 管理在线与匹配，对象存储/CDN 发布不可变资源包。首期共用仓库但保持边界，避免游戏逻辑、界面和钱包相互直接修改状态。

| 域 | 拟建对象 | 关键不变量 |
|---|---|---|
| 合作方与授权 | partners、apps、app_members、api_keys、game_entitlements | 密钥决定可信范围，合作方不能读取另一 App 的资源 |
| 游戏与版本 | games、rule_versions、math_profiles、asset_releases、app_game_configs | 已发布内容不可原地改写，新版本单独发布 |
| 会话 | players、game_sessions、launch_codes | 启动码短时、一次性；长期秘密只在服务端 |
| 多人比赛 | matches、seats、actions、snapshots、results | 一局一个规则快照，隐藏牌面只同步给对应玩家 |
| 概率周期 | probability_cycles、accepted_authorizations、cycle_results | 先资金责任受理，再固定一次完整周期结果 |
| 钱包操作 | wallet_operations、ledger_mirror、reconciliation_cases | 命令永久幂等、余额由合作方主账负责、未知状态可查单 |
| 发布与审计 | releases、approvals、audit_events | 生产变更可追溯；旧局继续使用原版 |
| 异步消息 | outbox、event_inbox、retry_jobs | 消息允许重复与乱序；通知不再次入账 |

**钱包与数据库边界。** 平台不会把自身数据库事务当作已经完成合作方钱包事务。先持久化业务意图，再投递命令并按原号查单；查明成功后才推进对局。以钱包最终凭据和双方分录对账，避免先给客户端“成功”再补写余额。全部写操作必须在正式数据库中落实唯一键和状态迁移，不能用前端按钮状态、内存 Map 或 Redis 过期键承担财务幂等。

**ID 约定。** 钱包资金命令 `request_id = operation_id`；命令重试更新传输时间和 nonce，保留业务号、路径和原始正文。事件的签名 request_id 等于 event_id，其 operation_id 引用原命令，进入独立事件收件箱去重。玩法目录、OpenAPI 示例和展示层使用同一游戏 ID，规则版本以 game-catalog.json 为准。

**展示与金额。** API 使用最小单位十进制字符串，示例 scale=2。管理页计算器只处理有限的演示档位，但仍先换算为最小单位、对总费用取整，再显示用户币；例如 3 人各 50 币、费率 3%：奖池 150、费用 4.50、奖励 145.50。正式服务与合作方钱包都使用整数运算。抽成、并列分奖和余数分配见规则册；余数只按已随机分配并冻结的 seat_index 补齐，不用用户 ID 决胜。

**界面原型。** 7 个关键页面覆盖总览、游戏目录、合作方 App、规则/RTP、局单、发布、接入文档。主色为墨绿、浅米白、低饱和金色，内容层级用留白与细边框区分。游戏封面来自已有概念图及原型资源。桌面优先，窄屏折叠导航并重排；金额、主操作和错误提示在窄屏仍可见。

**生产视图。** 当前生产切换仅用于验证界面状态，禁用示例应用创建、模拟运行及发布操作；不是生产账号权限。正式平台应由服务端 RBAC、App 授权和验证后的身份控制，不能信任前端隐藏按钮。

**规则与数学。** 10 款竞技的 V1 规则已按方案定义，首发变体固定，变更升版本。概率约 98%/99% 是开发目标，候选不能直接发布；正式模型报告包括数学配置、理论值或统计证据、置信区间、波动和完整周期最大派彩。管理页不把“目标 99%”当成已验证事实。

**渲染路线。** 2D/棋盘/牌类采用 PixiJS，场景型游戏采用 Three.js，固定镜头物理类独立计算动态物体。当前跑酷灰盒只证明简化场景的本地多客户端同步、动作裁定与同进程重连；最终物理、四角色骨骼、专业美术和真实手机性能继续由游戏阶段验收。

**下一阶段进入条件。** 以本目录规则、契约、资产计划和验收矩阵建立服务、数据迁移与测试。先完成两个隔离 App、一次性会话、真实持久化钱包命令和两款旧游戏适配，再接双质量样板。正式发布仍需真实合作方钱包、权限隔离、异常恢复、灰度回滚与实际 WebView 验收。
